# What's Real and What's Simulated

This project is a **teaching model**, built to make the mechanics of Classic
McEliece visible. It is explicit about which parts are cryptographically real
and which are illustrative, so it can be trusted by a technical audience.

## ✅ Real

- **Binary Goppa code over GF(2⁴).** `src/toy/` constructs a genuine binary
  Goppa code: real GF(16) field arithmetic (log/antilog tables), an irreducible
  Goppa polynomial `g(z)`, the parity-check matrix `H[j][i] = αᵢʲ / g(αᵢ)`
  expanded to binary, and a generator matrix computed as the null space of `H`.
- **Patterson decoding.** `pattersonDecode` is the real algorithm: syndrome
  polynomial `S(z) = Σ 1/(z − αᵢ) mod g`, inverse, square root in
  `GF(16)[z]/g(z)`, the extended-Euclidean split, and the error locator
  `σ(z) = α(z)² + z·β(z)²`. Its roots are the error positions.
- **The trapdoor gap.** The same ciphertext is decoded two ways: with `(L, g)`
  via Patterson (polynomial time) and without it via brute-force syndrome
  decoding (exponential). This is the actual security argument, demonstrated.
- **AES-256-GCM.** The KEM + DEM wrap uses the browser's WebCrypto
  `crypto.subtle` — real AES-256-GCM, real SHA-256, real `getRandomValues`.
- **NIST parameter sizes.** Every key/ciphertext size shown (e.g. the
  261,120-byte mceliece348864 public key) is the exact standardized value.

## ⚠️ Simulated or simplified

- **Toy parameters.** The live code uses `n = 16, k = 8, t = 2` over GF(2⁴) so
  every matrix and polynomial fits on screen. Real Classic McEliece uses
  GF(2¹²)/GF(2¹³), `n` in the thousands, and `t = 64…128`. The *structure* is
  identical; the *security* is not — the toy code is breakable by hand.
- **Panel 2's public-key bytes.** The 261 KB hex dump is generated by hashing a
  seed to the exact standardized length. It conveys real scale, but the bytes
  are not a real mceliece348864 key.
- **No constant-time guarantees.** The decoder branches on secret-dependent
  data and is not side-channel hardened. Do not use it for anything real.
- **Not the NIST KEM API.** No `crypto_kem_keypair/enc/dec` byte-exact I/O,
  no semantic-security transform (implicit rejection / KDF) as specified in the
  Classic McEliece submission.
- **Scrambling (S, P) is described, not applied.** The toy generator is used
  directly; the public-key scrambling `G_pub = S·G·P` is explained but not
  performed, since at toy size it adds no pedagogical value.

## For production

Use a vetted implementation such as
[liboqs](https://github.com/open-quantum-safe/liboqs) or the reference code from
the [Classic McEliece submission](https://classic.mceliece.org/).
